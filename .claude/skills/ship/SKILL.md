Выполни полный цикл разработки для: $ARGUMENTS

## Фаза 1 — Изучение задачи

Если $ARGUMENTS — число, прочитай задачу через GitHub MCP: title, body, labels, acceptance criteria.
Иначе работай с переданным текстом как с описанием фичи.

Зафиксируй задачи в TodoWrite.

## Фаза 2 — Изучение проекта

1. Прочитай CLAUDE.md — архитектура, стек, соглашения, API
2. Изучи структуру через Glob: `**/*.go`, `migrations/**`, `internal/**`
3. Найди через Grep все файлы, связанные с задачей (по ключевым словам из описания)
4. Прочитай найденные файлы и смежный код (handlers, services, storage одного домена)
5. Проверь существующие тесты (`**/*_test.go`) — понять стиль и паттерны
6. Построй в уме карту зависимостей: что вызывает что

## Фаза 3 — Планирование

Составь план одним абзацем:
- Какие файлы создаются / изменяются
- Нужна ли миграция БД
- Какие тесты будут написаны
- Есть ли риски или нетривиальные решения

Выведи план и **жди подтверждения от пользователя** перед реализацией.

## Фаза 4 — Реализация

После подтверждения:

1. Реализуй фичу строго по плану и правилам из CLAUDE.md
2. Соблюдай слоёную архитектуру: handler → service → storage
3. Следуй стилю кода в проекте (именование, обработка ошибок, логирование)
4. Не добавляй абстракций сверх необходимого
5. Если нужна миграция — создай файл в `migrations/` по шаблону goose
6. Отмечай выполненные задачи в TodoWrite по ходу работы

## Фаза 5 — Тесты

1. Напиши unit-тесты для новой логики (service / validation слой)
2. Покрой граничные случаи: пустые входы, некорректные значения, not found
3. Следуй стилю существующих тестов в проекте
4. Запусти тесты: `go test ./...` — все должны быть зелёными
5. Если `Makefile` существует — используй `make test`

## Фаза 6 — Линтер

Запусти линтер:
- Если есть Makefile с целью `lint` — `make lint`
- Иначе: `golangci-lint run ./...`
- Исправь все найденные замечания перед продолжением

## Фаза 7 — Self-review

Самостоятельно проверь реализацию перед коммитом:

**Корректность:**
- Все acceptance criteria из задачи выполнены?
- Граничные случаи обработаны?
- Ошибки возвращаются с правильными HTTP-статусами?

**Безопасность:**
- SQL-параметры через placeholders, не конкатенация строк
- Нет утечки чувствительных данных в ответах или логах
- Валидация всех входных данных на границе системы

**Качество кода:**
- Имена функций и переменных говорят сами за себя
- Нет лишних комментариев, объясняющих очевидное
- Нет дублирования — переиспользуются существующие утилиты

Если найдены проблемы — исправь их до коммита.

## Фаза 8 — Коммит и PR

1. Создай коммит:
   - Если $ARGUMENTS — номер issue: `feat: <краткое описание> (#$ARGUMENTS)`
   - Иначе: `feat: <краткое описание>`
2. Запушь ветку: `git push -u origin HEAD`
3. Открой PR через GitHub MCP:
   - Title: краткое описание фичи
   - Body: что сделано, почему именно так, как тестировать
   - Если есть issue — упомяни `Closes #$ARGUMENTS` в теле PR
4. Верни пользователю ссылку на PR
